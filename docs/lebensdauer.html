Warum Claude-Logins ablaufen

Gemessen an einer laufenden Installation, nicht aus der Dokumentation abgeleitet. Diese Seite haelt fest, wie Claude Code seinen Login verwaltet, wodurch gespeicherte Accounts sterben und welche Gegenmassnahme jeweils greift.

Woraus ein Login besteht

BestandteilOrtLebensdauer
Access-Token~/.claude/.credentials.jsonrund 8 Stunden
Refresh-Tokendieselbe Dateirund 30 Tage ab der letzten Nutzung
Kontodaten~/.claude.json, Felder oauthAccount und userIDCache, wird nachgeladen

Die Credential-Datei enthaelt nur Tokens, keinerlei Hinweis darauf, zu welchem Konto sie gehoeren. Diese Zuordnung steht ausschliesslich im Cache der zweiten Datei – deshalb muss ein Wechsel beide anfassen.

Der Refresh-Token rotiert

Verlaengert Claude Code den Login, bekommt es nicht nur einen neuen Access-Token, sondern auch einen neuen Refresh-Token. Der alte ist ab diesem Moment tot. Beobachtet an einem Wechsel um 10:47:02: unmittelbar danach wechselte der Refresh-Token in der aktiven Datei, waehrend der gespeicherte Profil-Snapshot noch auf dem Stand von 02:25 stand – und damit auf einem verbrauchten Token.

Daraus folgt die wichtigste Regel des Switchers:

Ein Profil-Snapshot ist nur so lange gueltig, wie sein Token seit dem Speichern nicht benutzt wurde. Jede Verlaengerung, die nicht ins Profil zurueckgeschrieben wird, macht den gespeicherten Stand wertlos.

Die zwei Arten zu sterben

1. Der Snapshot verpasst eine Verlaengerung

Frueher schrieb der Switcher den Snapshot nur bei save, switch und login. Alles, was Claude Code dazwischen verlaengerte, fehlte im Profil. Beim Wechsel zurueck landete der verbrauchte Token wieder in der aktiven Datei, und Claude Code meldete Login expired · Please run /login.

Gegenmassnahme: claude-account watch beobachtet die aktive Datei und schreibt jede Verlaengerung sofort ins zugehoerige Profil.

2. Der Refresh-Token laeuft ab

Auch ein perfekt gepflegter Snapshot stirbt, wenn das Profil rund 30 Tage nicht benutzt wird. Danach hilft nur ein neuer Browser-Login.

Gegenmassnahme: claude-account keepalive benutzt faellige Profile, bevor es zu spaet ist – siehe unten.

Auffrischen ohne Account-Wechsel

Der Trick ist CLAUDE_CONFIG_DIR: die Variable verschiebt beide Login-Dateien in ein beliebiges Verzeichnis. Damit laesst sich ein zweiter, vollstaendig getrennter Login betreiben, ohne den global aktiven anzufassen.

  1. Ein privates Arbeitsverzeichnis anlegen und den Profil-Snapshot als .credentials.json hineinlegen.
  2. Die echte Claude-CLI mit CLAUDE_CONFIG_DIR auf dieses Verzeichnis zeigen lassen und einen minimalen Request abschicken.
  3. Claude Code erneuert den Login dabei selbst und schreibt die neuen Tokens in dieses Verzeichnis.
  4. Das Ergebnis zurueck ins Profil, danach das Arbeitsverzeichnis restlos loeschen.

Vor dem Schreiben prueft der Switcher zusaetzlich, dass sich die global aktive Datei waehrenddessen nicht veraendert hat. Tut sie es doch, wird nichts uebernommen.

Warum kein eigener OAuth-Aufruf

Der Token-Endpunkt ist https://platform.claude.com/v1/oauth/token. Ein direkter Aufruf von dort ist trotzdem der falsche Weg: generische HTTP-Clients beantwortet Cloudflare mit Error 1010: browser_signature_banned. Die offizielle CLI zu benutzen ist nicht nur robuster gegen solche Sperren, sondern haelt auch den Token-Austausch dort, wo er hingehoert – ohne nachgebaute Client-ID und ohne eigene Fehlerbehandlung fuer einen fremden Flow.

auth status verlaengert nichts

Naheliegend, aber falsch: claude auth status liest die Datei nur und meldet loggedIn: true, selbst wenn der Access-Token laengst abgelaufen ist. Es findet kein Netzwerkzugriff statt. Nur ein echter Request loest eine Verlaengerung aus – deshalb schickt die Auffrischung einen minimalen Prompt.

Was bei einem gescheiterten Refresh passiert

Ist der Refresh-Token verbraucht oder abgelaufen, meldet Claude Code Failed to authenticate: OAuth session expired and could not be refreshed – und leert die Credential-Datei: leerer Access-Token, leerer Refresh-Token, expiresAt: 0.

Ein leerer Stand darf niemals einen gespeicherten ueberschreiben.

Sonst zerstoert genau der Mechanismus, der Accounts retten soll, den letzten brauchbaren Snapshot. Sowohl die laufende Sicherung als auch die Auffrischung pruefen deshalb vor jedem Schreiben, dass ein vollstaendiger Login dasteht.

Mehrere Sessions teilen eine Datei

Alle gleichzeitig laufenden Claude-Code-Prozesse benutzen dieselbe ~/.claude/.credentials.json. Verlaengert eine Session ihren Login, sehen das alle anderen. Laeuft eine Session mit Konto A noch, waehrend der Switcher auf B gewechselt hat, kann sie die Datei mit A-Tokens ueberschreiben.

Deshalb ordnet der Hintergrunddienst nur zu, was Claude Code selbst bestaetigt. Ist der Identitaets-Cache leer – der Zustand direkt nach einem Wechsel – wartet er, statt auf den Switcher-Status zurueckzufallen. Verloren geht dabei nichts: sobald Claude die Kontodaten kennt, wird der dann aktuelle Stand gesichert.

Wie geschrieben wird

Claude Code schreibt die Credential-Datei ueber eine temporaere Datei und rename. Zwei Konsequenzen:

  • Ein Symlink von ~/.claude/.credentials.json auf eine Profildatei funktioniert nicht – der erste Schreibvorgang ersetzt ihn durch eine echte Datei.
  • Zur Aenderungserkennung gehoert die Inode-Nummer. Zeitstempel und Groesse allein wuerden einen Tausch mit identischen Werten uebersehen.
